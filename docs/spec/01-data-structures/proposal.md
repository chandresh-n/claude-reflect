# Proposal

## Role

A proposal is a single candidate change to the configuration, generated by
the proposer, realized as a diff by the author, and presented to the human
for review. Proposals are the atomic unit of the meta-harness's output.
Multiple proposals form a batch; each proposal is independently reviewable.

## Inputs

Generated by the proposer in run loop Phase 5a. Diffs are produced by the
author in run loop Phase 5b. Reviewed by the human in Phase 7.

## Outputs

A proposal is held in memory during a run and becomes a decision record
at Phase 8 (decision commit) or at Phase 5b (if the author fails to
realize the diff). After becoming a decision record, the proposal itself
does not persist separately; the decision record carries its fields.

During a run (Phases 5a through 8), the proposal exists as a coherent set
of fields shared between the proposer, author, human-facing rendering,
and the decision commit logic.

## Schema

### The proposal record

- **proposal_id**: stable identifier assigned at generation. Propagated
  to the decision record.
- **batch_id**
- **run_id**
- **created_at**: when the proposer produced the intent (end of Phase 5a).
- **title**: one-line heading, human-facing.

- **why**: evidence section:
  - `cited_gaps`: list of `{gap_id, addressing_note}`.
  - `cited_sessions`: list of `{session_id, turn_range}`.
  - `cited_prior_decisions`: list of `{decision_id, relational_note}`.
  - `prose_summary`: paragraph combining the above for the human.

- **what**: the change summary:
  - `diff_reference`: git commit or branch hash. Populated by the author
    at Phase 5b. `null` between Phase 5a and the author's completion.
  - `files_touched`: list of paths. Populated by the author.
  - `short_description`: one-line mechanical summary.

- **how**: prose explaining the mechanism.

- **prediction**: prose articulating expected impact.

- **structural_tags**:
  - `change_type`: addition, modification, removal, restructuring.
  - `surface`: claude_md, skill, agent, hook, settings, mcp.
  - `novelty_status`: normal, forced_novelty, null_baseline.
  - `exploration_rationale`: prose, present only when `novelty_status`
    is forced_novelty or null_baseline.

- **authoring_addendum**: structured specification from proposer to
  author. Not shown to the human; committed in the decision record for
  audit. Fields:
  - `actions`: list of `{type, target_path}` where `type` is one of
    `create`, `modify`, `delete`.
  - `purpose`: prose, framed for the author's implementation context
    (distinct from `how`, which is framed for the human reader).
  - `activation_conditions`: if applicable (skills, hooks), when should
    the authored artifact fire? Prose or structured, as appropriate.
  - `behavior_constraints`: list of "must do" and "must not do"
    statements.
  - `examples`: concrete input/output examples when relevant.
  - `style_hints`: conventions to follow (e.g., "match the tone of
    existing skills under `.claude/skills/`").
  - `reference_material`: list of paths the author should consult for
    consistency before writing.

### The proposal batch

A batch wraps proposals generated in a single run.

- **batch_id**
- **run_id**
- **created_at**: end of Phase 5b (when all proposals in the batch have
  diffs, or have been marked author_failed).
- **window**: `{start, end}` dates of the session window reviewed.
- **proposal_ids**: list of proposal identifiers in this batch.
- **batch_narrative**: short prose summary the human reads first.
  Names how many proposals, what kinds of gaps they target, whether any
  are forced-novelty or null-baseline (with reasoning in the narrative).
- **contains_forced_novelty**: boolean. If true, the narrative explains
  which proposal is the forced-novelty one and why this region was
  chosen.

## Invariants

- Every proposal belongs to exactly one batch.
- `proposal_id` is immutable from generation through decision commit.
- Every `cited_gaps` entry resolves to a real gap record.
- Every `cited_sessions` entry resolves to a session in the run's window.
- Every `cited_prior_decisions` entry resolves to a real prior decision.
- At end of Phase 5a: `what.diff_reference`, `what.files_touched` are
  `null`. All other fields populated.
- At end of Phase 5b (for proposals that were authored successfully):
  `what.diff_reference` and `what.files_touched` are populated; the diff
  references a git artifact that merges cleanly into the active
  configuration.
- `files_touched` matches the actual diff's file set.
- If `novelty_status` is `forced_novelty` or `null_baseline`,
  `exploration_rationale` is populated.
- If `novelty_status` is `null_baseline`, the authored diff strips the
  configuration to its minimum (no skills, no hooks, minimal `CLAUDE.md`);
  this is enforced by the author agent's specification.
- At proposal creation (end of Phase 5a), the proposer appends
  `proposal_id` to the `related_proposals` list of every gap record in
  `cited_gaps`. This write happens before the proposal is handed to the
  author.

## Explicitly excluded

- No priority ranking within the batch. The human reviews proposals on
  their merits; ordering in the rendered markdown is navigational.
- No estimated cost of human decisions. The proposer does not say "if
  you reject this, future runs will waste N hours."
- No alternatives the proposer considered. One proposal = one option.
- No confidence scalar.
- No acceptance mechanism details in the schema. The mechanism by which
  the human marks accept/reject is an interface concern, specified in
  `05-interfaces/human-review.md`.
