# Implementation notes

This file captures decisions about *how* the meta-harness is built, distinct
from *what* it is (the spec) and *why* (the PRD). It exists for the
implementer (Claude Code, in our case) to read alongside the spec so that
implicit choices that would otherwise be invented are pinned down.

Read after the spec. The spec specifies contracts and invariants. This file
specifies the implementation context within which those contracts are
realized.

## Language and runtime

The meta-harness is a hybrid Python + bash implementation.

**Python** for orchestration logic, agent invocation, knowledge base
mutations that need transactional semantics, anything involving complex
data structures or cross-component coordination.

**Bash** for high-volume file I/O and git operations: setup scripts, file
walking, simple JSON manipulation with `jq`, git commit and branch
operations, scanning Claude Code's session log directory. Bash scripts are
called from Python via `subprocess` where appropriate.

The split principle: if the operation is "do this thing across many files
quickly" or "run a git command," bash. If the operation is "coordinate this
multi-step workflow with structured records," Python.

Python version: 3.11 or newer. At implementation time, use the current
stable Python release (whatever 3.11+ point release is current).

## Agent invocation

Agents (evaluator, proposer, author) are invoked via the Anthropic Agent
SDK. The SDK gives tool-use scaffolding for free, which the evaluator and
author both need (evaluator runs verification tools, author reads
configuration state).

Agents run as **standalone Python processes**. The meta-harness is its own
program; agents are functions/classes within it that call the Anthropic API
via the Agent SDK. The meta-harness is not a Claude Code subagent. It is a
separate tool that operates on Claude Code's configuration files and reads
Claude Code's session logs.

Each agent invocation creates a fresh SDK session. No shared state between
evaluator and proposer or between separate author invocations. The spec's
context-isolation invariant is enforced at the SDK-session boundary.

## Default models

- Evaluator: Sonnet (default).
- Proposer: Opus (default; this is the hardest reasoning).
- Author: Sonnet (default; writing config files, doesn't need top-tier).

All three are configurable per the meta-harness config file (see below).

## Token tracking

Every run logs token usage by agent and by phase. The run summary at Phase 9
includes total tokens consumed and an approximate cost figure (computable
from the model rates). No fixed budget; the meta-harness does not refuse to
run when costs exceed a threshold.

## Storage layout

The knowledge base lives at `.meta-harness/` parallel to `.claude/` inside
the target repository. Layout:

```
.meta-harness/
├── config.yaml                  # User configuration
├── gaps/
│   └── <gap_id>.json            # One file per gap record
├── archive/
│   └── <entry_id>.json          # One file per archive entry
├── summary/
│   ├── index.md                 # Regenerated by maintenance
│   ├── gap-kinds/
│   │   └── <kind>.md
│   ├── archive-entries/
│   │   └── <entry_id>.md
│   ├── exploration-profile.md
│   ├── gap-dashboard.md
│   ├── session-clusters/
│   │   └── <cluster_id>.md
│   └── decision-lineages/
│       └── <lineage_id>.md
├── runs/
│   └── <run_id>/                # Full transcripts and logs per run
│       ├── evaluator-output.json
│       ├── proposer-output.json
│       ├── author-<proposal_id>-output.json
│       └── run-summary.md
└── maintenance.log              # Append-only maintenance pass log
```

Records are stored as JSON files, one per record. Git-diffable. Each record
is independently inspectable. The proposer reads them directly (Claude reads
JSON well; no schema parser needed).

## Git structure

- **Active configuration branch.** The user's working branch (typically
  `main`). Accepted proposals merge their diffs here. The meta-harness does
  not commit to this branch; the merge of an accepted proposal's branch is
  what touches it.
- **Decisions branch.** Named `meta-harness/decisions`. Holds decision
  records as commits. Each decision is one commit with the decision JSON in
  the commit body and structured metadata in the commit message header
  (proposal_id, run_id, status, targeted_gaps).
- **Proposal branches.** Named `meta-harness/proposal/<proposal_id>`.
  Created by the author in Phase 5b. Either merged into the active
  configuration branch (on acceptance) or deleted (on rejection or
  author-failure) at Phase 8.

The proposer's run-level reasoning commit is on the decisions branch, with
the run_id in the commit message and the candidate analysis in the commit
body.

## Skill invocation

The meta-harness ships as a pip-installable Python package providing a CLI:

```
pip install meta-harness
cd my-repo
meta-harness review --since "last week"
```

Common subcommands:

- `meta-harness review`: invoke a run. Date range via `--since` or
  `--from`/`--to`.
- `meta-harness review --resume <run_id>`: resume a paused run from
  Phase 7 (after editor crash or human pause).
- `meta-harness status`: show the current state: active configuration
  archive entry, open gap records summary, pending proposals, last run.
- `meta-harness maintenance`: manually trigger a maintenance pass.

The Claude Code skill wrapper comes after the CLI is solid. A Claude Code
skill is added that wraps the CLI and lets the human invoke from inside
Claude Code. The skill wrapper is a thin layer; the CLI is the canonical
interface.

First invocation in a new repo automatically runs Phase 1 (environment
setup) silently. The user does not need to install or configure the
knowledge base separately.

## Configuration file

The meta-harness has its own configuration at `.meta-harness/config.yaml`.
First-run setup creates this file with defaults; the user can edit
afterward.

Fields:

```yaml
models:
  evaluator: claude-sonnet-4-...
  proposer: claude-opus-4-...
  author: claude-sonnet-4-...

maintenance:
  trigger_thresholds:
    new_sessions: 10
    new_decisions: 5
    new_gap_records: 3
    days_since_last: 7

stale_gap_threshold_sessions: 30

forced_novelty:
  probability: 0.20
  null_baseline_probability: 0.01

window_warnings:
  small_window_threshold_sessions: 3
  large_window_threshold_sessions: 50

logging:
  default_verbosity: quiet  # quiet | verbose
  save_full_transcripts: true
```

Defaults shown are starting values, not commitments. Implementation may pick
different defaults based on observed behavior.

## Logging

Default mode: quiet. The user sees:
- Phase boundaries as terse status lines ("Evaluating 19 sessions...",
  "Generating proposals...", "Authoring diffs...").
- The proposal batch markdown opening.
- The run summary at Phase 9.

`--verbose` mode adds:
- Full agent outputs streamed to stdout as they arrive.
- Tool-call traces from agents.
- Detailed timing per phase.

In all modes, full agent transcripts are saved to
`.meta-harness/runs/<run_id>/` for later inspection.

## Error handling

**API errors (rate limits, network, model errors):** retry with exponential
backoff (3 attempts: 5s, 30s, 120s). After 3 failures, crash with a clear
error message naming the phase, the agent, and the run_id. The run is left
in a partial state on disk; the user can re-invoke with `--resume <run_id>`
once the underlying issue is resolved.

**Agent produces malformed output:** the agent is given one retry with a
correction prompt. If the second attempt is also malformed, treat as a hard
failure and crash.

**Author cannot produce a valid diff:** not an error. The proposal is
marked `author_failed` and the run continues. Human sees this in the batch
markdown.

**Crash mid-Phase 4 or Phase 5 (before human review):** on next invocation,
the meta-harness detects the partial run directory and offers to discard or
resume. First version: discard only. Resumption from Phase 4 or 5 is
deferred (see `06-cross-cutting/deferred.md`-equivalent in the spec).

**Crash during human review (Phase 7):** the markdown file is on disk with
whatever decisions the human has marked so far. `meta-harness review --resume
<run_id>` re-opens the same markdown and the same diffs. Human completes
their review. Phase 8 commits decisions for whatever the human marked.

## Testing

Layered testing strategy:

**Unit tests.** For data structure read/write, schema validation, git
operations, summary layer regeneration. These are deterministic and
TDD-friendly. Use TDD for the bottom half of the stack. Aim for high
coverage on data structures and storage operations.

**Integration tests with fixtures.** End-to-end runs against synthetic
JSONL session logs. Verifies the run loop produces sensible decisions
without depending on actual LLM behavior. Mock the agent invocations with
canned responses for deterministic tests.

**Integration tests with real session logs.** A separate test suite that
runs against real Claude Code session logs (from a maintained corpus, or
the developer's own logs). These are not in the deterministic CI run; they
are run periodically to catch regressions in agent behavior.

**Behavioral tests.** A small fixture set with known patterns, asserting
the evaluator identifies expected gap kinds. Flaky due to LLM
nondeterminism but useful as smoke tests. Run nightly or on releases.

**Manual evaluation.** For agent quality. Run on real session logs, review
outputs by hand. The implementer (you) is the primary evaluator; LLM-as-judge
can supplement for prompt iteration.

## Fixture generation

Build a small utility, `meta-harness fixtures generate`, that produces
synthetic JSONL session logs with known patterns. Useful for:

- Integration tests (deterministic input).
- New users who want to try the meta-harness before they have real session
  history.
- Reproducing bugs (the user can run the fixture generator with the same
  seed to recreate a specific scenario).

Pattern types the fixture generator supports at minimum:

- Sessions with file-location struggles.
- Sessions with test failures.
- Sessions with correction passes.
- Sessions with refinement passes.
- Sessions with retry passes.
- Sessions with hallucinations.
- Sessions with tool call loops.
- Clean one-shot sessions (no notable patterns).

The generator's output is JSONL files matching Claude Code's session log
format closely enough that the meta-harness reads them as if they were
real.

## Implementation order

Build smallest to largest. Each subtask is its own Claude Code session with
a fresh context, pointing at specific spec files. Suggested order:

1. **Knowledge base directory structure and setup script.** Phase 1 of the
   run loop. Creates `.meta-harness/`, initializes git branches, writes
   default config. Spec: `04-processes/run-loop.md`,
   `02-storage/knowledge-base.md`.

2. **Gap record read/write.** JSON file operations, schema validation.
   Spec: `01-data-structures/gap-record.md`.

3. **Decision record read/write and git operations.** Commits to the
   decisions branch with structured messages. Branch and merge handling
   for proposal branches. Spec: `01-data-structures/decision-record.md`,
   `02-storage/decisions-git.md`.

4. **Archive entry read/write.** JSON files plus archive lifecycle (active
   vs. superseded). Spec: `01-data-structures/archive-entry.md`.

5. **Session log reading utilities.** Walk Claude Code's session log
   directory, parse JSONL, filter by date range, expose a session
   abstraction. Spec: `02-storage/session-logs.md`.

6. **Summary layer storage and index regeneration.** Page kinds,
   filesystem layout, index regeneration logic. Spec:
   `02-storage/summary-layer.md`.

7. **Maintenance process.** Triggered by content thresholds. Walks
   knowledge base, regenerates summary layer pages, transitions stale
   gaps, reconciles kind vocabulary, commits maintenance log. Idempotent.
   Spec: `04-processes/maintenance.md`.

8. **Evaluator agent.** Reads sessions, produces evaluation report,
   updates gap records as side effect. Spec: `03-agents/evaluator.md`,
   `01-data-structures/evaluator-output.md`.

9. **Proposer agent.** Reads evaluation report and knowledge base,
   produces proposal intents (rationale + addendum). Spec:
   `03-agents/proposer.md`, `01-data-structures/proposal.md`.

10. **Author agent.** Takes proposer intent, produces git diff on a
    proposal branch, or reports failure. Spec: `03-agents/author.md`.

11. **Run loop orchestration.** Phases 0 through 9, including pending
    proposal handling and resume semantics. Spec:
    `04-processes/run-loop.md`.

12. **CLI and skill invocation.** The `meta-harness` command-line tool.
    Subcommands: `review`, `status`, `maintenance`. Includes the Claude
    Code skill wrapper. Spec: `05-interfaces/skill-invocation.md`,
    `05-interfaces/human-review.md`.

Each subtask is bounded enough to fit in a single Claude Code context. By
the time you reach the agents (steps 8-10), the data structures are
concrete and unambiguous. By the time you reach the run loop (step 11),
all the pieces it orchestrates exist.

## Agent prompts

Agent prompts (the system prompts that define each agent's behavior) are
generated by Claude Code as part of implementing each agent. The
behavioral directives in each agent's spec file constrain the prompt:

- Skepticism, evidence-grounded prose, no grading, exhaustive (evaluator).
- Multi-dimensional prioritization, evidence-grounded, historical
  awareness, simplicity criterion (proposer).
- Honor the addendum precisely, match conventions, write for Claude Code,
  fail honestly (author).

Initial prompts are first drafts. They are iterated through:

1. LLM-as-judge evaluation against a fixture set of known cases.
2. Manual review of agent outputs on real sessions.
3. Adjustment of prompts based on observed drift or failure modes.

The prompt iteration loop is part of the system's bring-up, not a one-time
implementation step. The prompts will not be perfect on first
implementation; they need to be honest about the spec's behavioral
directives and improvable from there.

## Implementation cautions

Constraints worth restating because Claude Code may drift on them during
implementation:

- **No scalar grades anywhere.** Anywhere Claude Code is tempted to
  compute a quality score, an effort score, or a priority number, it
  must resist. The schemas don't have these fields by design. Adding them
  as "convenience" violates an architectural commitment. If a function's
  signature includes a numeric score, that's a smell.

- **Agent context isolation.** Implementation will be tempted to share
  state between agents for efficiency: pass the evaluator's in-memory
  output directly to the proposer, share an Anthropic API client across
  agents with conversation history retained, etc. Resist. Each agent
  gets a fresh API client/session. Communication happens through disk
  (JSON files, git, the knowledge base), not through shared in-memory
  state.

- **Summary layer is not authoritative for decisions.** When the proposer
  needs current gap state, it reads gap record JSON files, not the
  gap-dashboard summary page. The summary layer is for orientation and
  navigation, not for proposer judgments. Implementation should make this
  enforceable: code paths where the proposer queries authoritative state
  should hit the canonical layer, not the summary cache.

- **Idempotent maintenance.** Maintenance must be idempotent: running it
  twice produces the same result the second time. Test this explicitly.
  A common failure: maintenance that updates timestamps on every run
  even when content hasn't changed. The fix is to detect "no new content
  since last pass" and exit early.

- **Append-only knowledge base.** Records are never deleted. Specific
  fields can update (gap record evidence appends, decision status
  transitions). All other fields are immutable post-write. Implementation
  should have safeguards: write operations check whether the file exists
  before creating; record updates touch only the fields the spec allows
  to update; tests verify that "deleting" a record is impossible through
  normal API.

- **Markdown batch document is plain.** When the meta-harness writes the
  proposal batch markdown for human review (Phase 6), the formatting is
  plain: simple headings, simple checkbox-style decision capture, no
  fancy tables, no decorative elements. Claude Code drifts toward
  elaborate formatting if not constrained; the human-review interface
  benefits from being boring.

- **Crash recovery is simple in v1.** Sophisticated resume semantics for
  Phase 4 or Phase 5 crashes are deferred. First version: detect partial
  run directory on next invocation, offer to discard, start over.
  Resumption is supported only for Phase 7 (post-evaluation, post-proposer,
  post-author, awaiting human review).

## What this file is and is not

This file is implementation guidance, not the spec. The spec is
authoritative for contracts and invariants. This file is authoritative for
implementation choices that are not in the spec because they are
implementation, not contract.

If a conflict arises between this file and the spec, the spec wins. This
file should be updated to remove the conflict.

This file is a living document during implementation. As Claude Code
encounters questions not answered here, this file is updated with the
answers (rather than letting the answers live in code or comments). At the
end of implementation, this file should be a complete record of every
non-trivial implementation decision.
