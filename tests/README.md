# `tests/` — Test suites

Earmarked for the layered testing strategy described in
`docs/IMPLEMENTATION.md` (section "Testing").

## Layout

```
tests/
├── unit/             # Deterministic, TDD-friendly. Data structures, schema validation,
│                     # git operations, summary-layer regeneration.
├── integration/      # End-to-end runs against synthetic JSONL session logs.
│                     # Mock agent invocations with canned responses for determinism.
│                     # Also: a separate suite that runs against real session logs,
│                     # not on the deterministic CI path.
└── fixtures/         # Synthetic JSONL session logs and other test inputs.
                      # Generated by `meta-harness fixtures generate` (see src/meta_harness/fixtures/).
```

## Test categories (from IMPLEMENTATION.md)

1. **Unit tests** — high coverage for the bottom of the stack: records,
   storage, git ops, summary-layer regeneration. TDD-friendly.
2. **Integration tests with fixtures** — deterministic; mock the LLM agents.
3. **Integration tests with real session logs** — periodic, not on CI.
4. **Behavioral tests** — small fixture set with known patterns; assert
   evaluator identifies expected gap kinds. Flaky by nature; nightly only.
5. **Manual evaluation** — humans review agent outputs on real sessions.

## Fixture pattern types to support

`meta-harness fixtures generate` should at minimum produce sessions with:

- File-location struggles
- Test failures
- Correction passes
- Refinement passes
- Retry passes
- Hallucinations
- Tool call loops
- Clean one-shot sessions (no notable patterns)

JSONL output should match Claude Code's session-log format closely enough
for the meta-harness to read it as if it were real.

## Idempotency tests

Maintenance must be idempotent. Add an explicit test that runs maintenance
twice in a row and asserts the second run is a no-op (per the
`docs/IMPLEMENTATION.md` caution).
